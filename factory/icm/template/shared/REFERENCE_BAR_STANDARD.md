# Reference-bar standard

Use this when taste, quality, or comparative performance matters.

A useful bar is:

1. **Named** — a specific shipped page, product, article, repository, benchmark, standard, or artifact.
2. **Fetchable** — the reviewer can inspect the real thing rather than a description of it.
3. **Comparable** — ours and the reference can be placed side by side or measured against the same test.

When a measurable half exists, pair the reference with the number: load time, pass rate, bundle size, task completion, accessibility result, cost, or another relevant metric.

## Builder / critic rule

The builder does not perform the only comparison.

A fresh critic:

1. opens the actual output;
2. opens the actual reference;
3. compares the relevant piece directly;
4. says which is stronger for the stated intent;
5. names the single largest remaining gap;
6. returns the gap to Build or Blueprint.

Praise is optional. Evidence is not.

## Loop boundary

Keep improving while the approved scope, cost, safety, and consequence boundaries still hold. Stop and escalate when:

- the next improvement changes the approved product or architecture;
- cost exceeds the approved budget;
- a legal, rights, safety, privacy, security, destructive, or production decision appears;
- the reference is unreachable or no longer comparable;
- evidence shows the reference is the wrong standard for the actual user.

Do not use an arbitrary round count as the quality bar. Do not use an unbounded loop to bypass Vibe Judge or human authority.
